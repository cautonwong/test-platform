# 场景测试层

场景用例必须显式列出参与的被测设备与周边设备(按 `id` 点名),不靠隐式遍历或默认设备集:
单台设备合格不代表场景通过,参与方写不清楚就没法判结论归谁。

形状定在 `docs/adr/0005-scenario-layer-shape.md`,一句话:**一条场景就是一个 pytest 函数**,
和一致性层同一套机制,没有步骤表、没有基类、没有场景库。每个场景跑完,证据会话目录下多一份
`scenario-<用例名>.json`:参与方 id 与 role、引用的读数键、每步结果、场景结论
(`passed` / `failed` / `invalid`)与关联的 per-device JSONL 文件名 —— 第三方据此能自己复核
"这个场景为什么算通过",不必读终端。

## 现有用例

`test_grid_frequency.py`:

- 正例:电网模拟器设定 50Hz → 逆变器读数 → 判据集求值合格 → 场景 `passed`。
- 反例:同一台逆变器的应答改成 60Hz(判据 45–55Hz)→ 单台设备不合格 → 场景 `failed`。
  单台合格不等于场景通过,反过来也一样。
- 设定 → `settle(0.2, ...)` → 读 → 判:等待落成记录里的一步(`device: null`、`detail` 带
  `target_s` / `actual_s`),它本身不判通过。时长取 0.2 秒,默认套件不为它多花看得出来的时间。

## 场景结论的三种值

| verdict | 含义 | 由谁的不成立决定 |
|---|---|---|
| `passed` | 每一步都成立 | —— |
| `failed` | 被测设备不合格 | 至少一个 `role: dut` 的步骤 |
| `invalid` | 测试无效,不是设备不合格 | 只有 `role: support` 的步骤 |

每一步的 `passed` 必须是实际求值结果(判据集的 `passed`、设备回报与设定值的比较),
不许写成字面量 `True` —— 写死的那一步等于没有断言。

## 不做什么

分支、循环、并发、等待到条件、步骤级重试、场景调用场景、批量参与,这些现在都不支持,
每条的原因与重新审视的信号写在 ADR-0005 的清单里。要加形状时先改那份清单。

`settle` 等固定时长不在"等待到条件"之列:条款规定的物理时长不随机器快慢变,结论也就不随机器快慢变。
它只记时长、不判合格,失败归因仍只看有设备的步骤。

本目录在 `pyproject.toml` 的 `testpaths` 里(有真实用例,默认套件会跑);
`tests_unit/test_scenario_layer.py` 双向守卫"有用例 ⇔ 在 testpaths",两边不一致时收集期就红。
