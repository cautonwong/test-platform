# 终端与周边设备进同一设备模型,靠 `role` 与 `via:` 区分身份

Status: accepted

电网模拟器、可调负载、标准源和采集终端都写在 `devices.yaml` 同一个 `devices` 列表里,共用型号、点表、
驱动注册表和拓扑排序 —— 它们是"必须被平台控制的设备",不是夹具细节,不给它们再造一套机制。
身份只由两个字段区分:`role: dut | support` 决定判不判合格(`support` 挂掉等于测试无效,不是被测设备不合格),
`via:` 决定接入从属关系(终端下的表共享终端那条总线,自己不建物理连接)。

## Considered Options

- **台架设备做成 pytest fixture / 测试脚手架** —— 否决。它把台架的生命周期绑在用例上,
  但"先连周边、再连被测"是物理顺序,与用例执行顺序无关;而且并行时按总线分组要用到拓扑,
  fixture 里拿不到,只能再补一套拓扑描述。
- **周边设备单独一份清单 + 单独一套装配** —— 否决。会得到两条几乎一样的装配路径
  (校验、连接顺序、失败语义、证据),差别只有"判不判合格";两份实现迟早不同步。
- **同一 `devices` 列表 + `role` / `via:` 两个字段** —— 选中。装配只有一条路径,
  身份差异收敛到两个字段上,新增一种周边设备是"加型号 + 加驱动",不是"加机制"。

## Consequences

- 周边设备连接失败 → 整轮 `tests/` 会话 skip(实测 58 skipped、0 failed),不判任何被测设备不合格。
  对物理台架是诚实的:台架不在,全部结论无效。粒度偏粗,见下面的重新审视条件。
- 契约测试只对 `role: dut` 展开,周边设备不会被当成"某一类设备的所有实例"重复判定。
- `via:` 指向的设备必须是 `role: dut`,且下游设备不能再写 `connection`:共享上游那条总线,
  写了也不会生效,所以装配前直接拒绝,不静默忽略。
- 周边设备不声明 `criteria` —— 不判合格,就没有合格线。上游 legacy 的 7 类操作对象没有全部造成空壳,
  落地的是机制 + 一种真实类型(三相电网模拟器),其余等真实台架需求。

## 重新审视的条件

需要"只有部分用例依赖台架"时(`role` 的二分不够表达),要引入设备依赖声明,那属于场景层;
或者周边设备自身需要合格判定(台架自检),那时 `support` 与 `dut` 的二分要重新画,
不再能用"support 不判合格"一句话带过。
