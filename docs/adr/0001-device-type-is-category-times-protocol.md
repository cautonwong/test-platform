# 设备类型 = 大类 × 规约,型号差异只出现在配置里

Status: accepted

同一大类的设备换一个规约,读法完全不同(电表走 Modbus RTU 还是 DL/T645,帧、地址、编码都不是一回事);
同一规约换一个型号,只差地址、倍率、字节序。所以驱动注册键取 `(设备类型, 规约)` 二元组
(`drivers/registry.py`),型号差异全部下沉到 yaml 的点表里 —— 新增同规约型号零 Python 文件。
代价是不对称的:新增一个规约要写一个协议模块,新增同规约型号只改 yaml,这个不对称是刻意的。

## Considered Options

- **按型号注册驱动(一型号一工厂)** —— 否决。几十个型号意味着注册表和驱动文件线性膨胀,
  而型号之间差的只是点表几行;把配置写成代码,改一个寄存器地址要发版。
- **只按大类注册,规约写在驱动里分支** —— 否决。给电表加 DL/T645 时,同一个工厂里就要长出
  `if protocol == ...`,这是 5a/5b 真正想避免的那条分叉;5b 验证过:通用读取路径零改动。
- **二元组键 + 点表配置** —— 选中。规约是"怎么读",型号是"读哪儿、怎么换算",
  前者是代码,后者是数据,边界与"第二个规约不应该改驱动"这条验收标准一致。

## Consequences

- 新增同规约型号:只改 `configs/devices.yaml` 的 `models` / `devices` 两段。
- 新增规约:`protocol/` 一个模块 + 驱动里一个 `read_raw` 工厂 + `PROTOCOL_ACCESS` 一行。
- 同一个 `(类型, 规约)` 重复注册直接抛错,不会后来者静默覆盖前者。
- 清单里型号的 `type` / `protocol` 对不上已注册键时,装配时报错并列出已注册的键,
  而不是回退到"看起来能跑"的默认实现。

## 重新审视的条件

同一台设备需要同时支持两种规约(双规约表、或运行期协商规约)时,`(类型, 规约)` 这个键
就不再由型号唯一决定 —— 那时要把规约挪到设备实例上声明,或引入一次显式的规约探测。
今天没有这种设备,清单校验(`PROTOCOL_ACCESS`)也假定一台设备只有一条规约。
