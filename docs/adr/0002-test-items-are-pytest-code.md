# 测试项用 pytest 代码写,不做自定义描述语言

Status: accepted

测试项就是一个 pytest 函数:断言、fixture、参数化、跳过都用 pytest 原生的;身份(编号、标准条款、标签)
靠 `@case` 挂在函数上,筛选靠 `--select` 与清单里的 `test_matrix`,读的是同一份元数据。
不造 DSL 的理由:门槛要低到测试工程师能自己写;写不动的人由 agent 代写代码,而不是再发明一门语法让他学。

## Considered Options

- **自定义 DSL / YAML 用例描述(上游 legacy 平台的形态)** —— 否决。一门语法要自带解析器、错误定位、
  IDE 支持才算能用;真实用例迟早需要循环、条件、超时、重试,DSL 最后会长成半门编程语言,
  而调试只能看平台自己的日志。上游 legacy 平台已经证明这条路要长期给"用例外的东西"做维护。
- **配置化阈值 + 代码用例(选中的形状)** —— 不是"什么都不配置",而是分清哪些该配置:
  *跑哪些用例* 由 `test_matrix` 表达,*合格线* 由 `criteria_profiles` 表达,*怎么读* 由点表表达;
  *怎么测*(断言序列、等待、失败语义)留在代码里。配置改得动的是覆盖面与判据,不是逻辑。
- **模板 + 代写** —— 选中做配套:用例形状固定成 `docs/WRITING_TESTS.md` 里的四种,写不动的人
  把意图说清楚由 agent 按模板产出代码,人只审编号与条款。

## Consequences

- 加一条测试项 = 加一个函数;不存在"第二份用例清单",身份只有 `@case` 这一个事实源,
  否则编号与矩阵必然漂移成两个真相。
- 按设备参数化却没有 `@case`、或不被任何型号矩阵覆盖的用例,收集阶段直接报错,不静默变成 0 条绿。
- 代价:新增用例的人要会写 Python(至少能读懂并改模板)。非程序员无法自助新增用例 ——
  这是刻意的取舍,换成 DSL 会把成本从"读代码"挪到"学语法并等平台支持"。

## 重新审视的条件

出现下面任意一条时,再考虑受限 DSL:测试工程师开始大量新增用例,而 agent 代写成为瓶颈;
或者用例逻辑收敛到很小的一组操作(断言 + 等待 + 记录),DSL 可以有界而不长成编程语言;
或者有非 Python 的使用者需要在无人辅助下自助改用例。三条都还只是猜时不要动手。
