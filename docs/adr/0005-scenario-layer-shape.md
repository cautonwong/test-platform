# 场景层是 pytest 代码 + 显式参与方声明,场景结论单独落盘

Status: accepted

场景测试层沿用 ADR-0002:一条场景就是一个 pytest 函数,参与方在函数开头按 `id` 点名(role 取自设备清单,
不在用例里重复),没有步骤表、没有解释器、没有基类。每跑一次场景,证据会话目录里另写一份
`scenario-<用例名>.json`:参与方与 role、引用的读数键、每步结果、场景结论与关联的 per-device JSONL。
理由和一致性层是同一条:写用例的人只需要会一段 Python,而"这个场景整体过没过"必须是**数据**,
不能只活在一次 `pytest` 的绿色里 —— 现在的证据只有 per-device 的读数与判据结论,
"单台合格 ≠ 场景通过"这个结论无处安放。

## Considered Options

- **YAML 步骤表 / 场景描述语言(上游 legacy 平台的形态)** —— 否决,而且是**用户级决定**:
  它会推翻 ADR-0002。一门语法要自带解析器、错误定位、变量引用才算能用;真实台架迟早需要
  "设定值不满足就重试""扫频",DSL 会一路长成半门编程语言,而调试只能看平台自己的日志。
- **场景基类 / 场景注册表 / 场景库** —— 否决。三条用例还看不出共性,基类会立刻把"哪些设备参与"
  藏进构造器或类属性,参与方就不再显式,而显式正是这一层唯一必须保住的东西。
  出现 5 个以上场景反复写同样三段(设定 → 读 → 判)时,先抽一个普通函数,不抽基类。
- **纯代码 + 显式参与方声明 + 落盘的场景结论(选中的形状)** —— 与一致性层共用 pytest 的全部机制
  (断言、fixture、`@case`、`--select`、skip 语义),只有一处新增:场景结论写成 `scenario-<用例名>.json`。

## 不支持的东西 —— 以及出现什么信号才重新考虑

这份清单比"支持什么"重要:场景层一旦开始长语法,它就会慢慢变成 ADR-0002 明确否决的那门语言。
每一条都写清"为什么现在不做"和"什么信号才回头"。

| 形状 | 为什么现在不做 | 重新考虑的信号 |
|---|---|---|
| 分支(按读数决定下一步、if/else 步骤) | 一条场景的步骤是固定的;出现分支通常意味着"这其实是两个场景",拆成两个函数即可 | 同一段前缀 + 分叉在 3 个以上场景重复,且拆开会让报告读不懂 |
| 循环(扫频、设定值列表、重复 N 次) | `@pytest.mark.parametrize` 已经能给"同一组步骤跑多个设定值",而且每个设定值在报告里独立成行;场景层自己写循环会把 N 个节点压成一个,失败只剩一行 | 参数化组合爆炸到报告读不动,且每一步需要上一步的结果当输入 |
| 并发(两台设备同时动作、验证时序先后) | 同一条总线上的设备本来就不能并行(拓扑与 `xdist_group` 的立场);真正的并发语义要时钟同步与事件排序,那是仿真器的事 | 出现"必须同时给两台设备发指令,并在 Δt 内验证响应顺序"的真实需求,且已有硬件能给出可重复的时间戳 |
| 等待/轮询到条件(等 30s 直到 SOC 降到 50%) | 判据层判的是一次读数;等待会让结论依赖机器速度,产出偶发红 | 设备确实有"下游反应慢"的物理行为,且有一份可重复的时序证据说明等待多久是物理的 |
| 步骤级重试 | 自动重跑会掩盖总线抢占型随机失败(`docs/WRITING_TESTS.md` 已禁止 `pytest-rerunfailures`);重试是掩盖机制,不是修复 | 无。要重试先证明那次失败不是平台自身的问题 |
| 场景调用场景 / 场景库 | 复用需要参数与返回值语义,那就是在造语言 | 3 个以上场景按相同顺序复现同一段步骤 —— 那时抽普通函数,各自仍显式声明参与方 |
| "所有逆变器一起"这类批量参与 | 参与方按 id 点名,一台一个名字;批量意味着默认设备集,而参与方写不清楚就无法判定结论归谁 | 真实台架上 N≥5 台同型号设备参与同一场景,手写 id 变得不可读(信号很弱,先不做) |

## 参与方按 id 显式点名

场景函数开头按 `id` 取设备(`composition_root.get("grid_sim_01")`),一台一行;不从
`all_drivers()` 遍历、不用"默认设备集"、不按类型展开。role 由清单给出(`role_of`),
因为它是设备清单的事实,不是用例的 —— 用例重复声明 role 会造出第二个真相,两边迟早不一致。

**参与方不自动展开:清单里加设备,场景用例一条都不多跑。** 两条测试层在这里有意不一致:

| 清单里加一台逆变器 | 覆盖变化 |
|---|---|
| `tests/` 契约用例(泛型 fixture `inverter` / `inverter_id`) | 自动多跑一个节点 `[inv_03]` |
| `tests_scenario/` 场景用例(按 id 点名参与方) | **一条都不多跑** |

这是有意的:场景的参与方写在代码里,覆盖范围才是这一层能说清的东西 —— "这个场景验证的是
grid_sim_01 与 inv_01 之间这件事",而不是"清单里每台逆变器都被这个场景测过了"。
什么时候改用泛型 fixture:出现"同一个场景要对清单里每台同类型设备各跑一遍"的**真实需求**时
(比如每条逆变器都要单独和同一台电网模拟器过一遍),不是"顺便让场景层跟着清单走"。

## 场景结论怎么算

结论只能来自实际求值:

- 周边设备那一步:`passed` 是"设定值与设备**实际回报**的比较"(不是"我发过了")
- 被测设备那一步:`passed` 是聚合根记下那条读数上的 `passed`,即判据集的求值结果

结论是这些步骤的聚合(`reporting/scenario.py::verdict_of`),失败落在谁身上决定措辞:

- 全部成立 → `passed`
- 有被测设备的步骤不成立 → `failed`(设备不合格)
- **只有**周边设备的步骤不成立 → `invalid`(测试无效,不是设备不合格)

任何一步的 `passed` 都不允许写成字面量 `True`:写死的那一步等于没有断言,它会让场景永远绿,
而这正是这一层存在的理由(单台合格 ≠ 场景通过,单台不合格也 ≠ 场景不通过)。

## Consequences

- 场景记录与 per-device JSONL 并排放在证据会话目录:`scenario-<用例名>.json`。字段
  `verdict` / `note` 与 `round-status.json` 同名同义;`participants` 给 id 与 role,
  `reading_keys` 给引用的读数键,`steps` 给每步动作与结果,`evidence` 给 per-device 文件名。
  per-device 格式一字未改 —— 新增的只是"整体过没过"这一份。
- 场景结论不跨轮聚合:它回答"这一轮这个场景为什么算通过",跨轮回归对比留给报告层。
- `tests_scenario/` 回到 `pyproject.toml` 的 `testpaths`。`tests_unit/test_scenario_layer.py`
  双向守卫"有用例 ⇔ 在 testpaths",两边不一致时收集期就红。
- 已知限制:周边设备**连接阶段**挂掉时,场景用例现在报红而不是 skip。那个转换点只有
  `tests/conftest.py` 一处,只对一致性层生效;要统一,得把"周边设备故障 = 测试无效"
  提取到所有层共用的位置,那是另一张票。

## 重新审视的条件

真实客户给的就是一张工步表、且要求非程序员自助编辑时;或者上面"不支持"清单里 ≥2 条被真实需求
同时撞上、且只能靠加语法解决时 —— 那时才讨论受限 DSL,并把它作为对 ADR-0002 的正式修订,
而不是在场景层悄悄长出来。
