# 协议知识独立成层,驱动走点表驱动的通用读取路径

Status: accepted

帧怎么拼、CRC 怎么算、编码与字节序怎么解,全部收在 `protocol/` 的纯函数里,不 import `transport/` 与 `domain/`。
驱动只剩一条通用读取路径:读数键 → 点表项 → 按规约取字节 → 解码 → 聚合根一次领域方法调用,
没有"一设备一方法"的读法。第二规约(DL/T645)接入时这条路径一行未改 —— 这是这个分层成立的标准,不是巧合。

## Considered Options

- **每类设备一个驱动、各自实现读法(第一版那种一设备一读方法的形态)** —— 否决。
  协议知识会散进驱动,第二个规约会把它复制一遍,CRC 与字节序的实现从此有两份,
  两份之间迟早分叉;协议层的单测也就没法脱离硬件写。
- **每个型号一个 `read_xxx` 方法** —— 否决。与 ADR-0001 冲突:型号差异只该出现在点表里,
  每加一个型号就多一个方法,几十个型号之后驱动变成一张方法表。
- **通用读取路径 + 专用驱动出口** —— 选中。需要时序或分支的设备(文本行协议的逆变器 / 电池、
  带协商步骤的终端)保留写专用 `read_raw` 的出口,但复用协议层与点表求值,
  通用路径不认设备类型、也不认型号名。

## Consequences

- 加规约 = `protocol/` 一个模块 + 驱动里一个 `read_raw` + 清单一行 `PROTOCOL_ACCESS`;
  通用读取路径与用例不动。
- 读数的解码单测可以脱离硬件跑:给定点表项与原始字节解出物理量,给定物理量拼出合法帧。
  CRC 用真实向量锁住(X25 / IBM 变体),不靠"跑通了"推断。
- 已知限制:`read(key)` 会把点表里的点全读一遍(判据要一次看全),真实串口下那是 N 次往返。
  今天没有高频读数场景,所以先不缓存;接真实设备后再按实测决定加缓存还是加批量事务。

## 重新审视的条件

需要"一次事务读多个点"(点表分页、连续寄存器块)或某设备的读数必须按固定顺序协商时,
通用路径要长出批量事务的能力 —— 那时先看协议层能否表达"一次收发多个点表项",
不要为此在驱动里重新分叉。另一个信号是:如果某个规约的 `read_raw` 开始复制解码逻辑,
说明分层被绕过了。
