# 台架设定:同一条款重复的是前置,被观测的才是步骤

Status: accepted

一份条款开头的台架设定(只加电压上电、接线方式、`Ua=Un / Ia=0 / Fre=Hz`)有两种性质,判据只有一条:
**它是"每条条款都要重复的前置",还是"被观测的变量"?**

- **前置** → 写成条款的一个 `bench:` 字段,形状复用 `initial_setpoint` 的 mapping(量名 → 值),**不进 steps**。
  理由:同一份 12 行设定在每一条条款前面都一样,塞进 steps 会让 105 条条款各重复一遍;而且它不是被测行为,
  只是"让表能测"的前提。写进 steps 还会和 `manual` / `write` 混在一起,报告里读不出"这步到底验了什么"。
- **被观测的变量**(把台架调到 X → 读表 → 判 Y)→ **场景层**。这类条款有因果链,`setting_cases` 的
  "写 → 读回 → 相等"表达不了;调台架本身就是要被检验的动作。

一条条款若同时含 `bench:` 前置与因果链步骤,整条归场景层,`bench:` 跟着场景用例走,不进 `setting_cases`。

## Considered Options

- **把台架设定当步骤写进 `setting_cases`(方案 A)** —— 否决。13通信 105 条条款**每条都含调整台体**,
  当步骤会让每条重复 12 行同义配置,而且逼着 `setting_cases` 长成一个步骤引擎(ADR-0002 反对的方向)。
- **带台架的条款一律归场景层(方案 B)** —— 否决。纯"写参数 → 读回 → 判等"的条款进场景层就是换壳,
  把逐台设备的一致性验证淹没在场景里。
- **按"前置 / 被观测"切开(选中的形状)** —— 前置进 `bench:` 字段,被观测变量的条款进场景层;
  纯写读回的仍归 `setting_cases`。

## Consequences

- `bench:` 里的量名必须走同一份对照表(`configs/import/params.yaml`),拼错在装配前报错 —— **不许另开一套名字**,
  否则同一台架量会有两套拼写,迟早漂开。
- 因果链条款需要 `hold`(把台架按设定保持一段时长)才能表达走字类语义;那是场景层的未完成部分。
- 导入器要按步骤类型分流:同一条条款进 `setting_cases` 还是场景用例,由"是否有被观测的台架动作"决定,
  这个判定必须是显式的、写在报表里,不许静默二选一。

## 重新审视的条件

出现"前置也要按条款变化"(不同条款前要不同的台架设定)时,`bench:` 字段可以带条件或引用,那时再讨论;
在此之前它就是一份静态 mapping,不要提前给它加表达式。
