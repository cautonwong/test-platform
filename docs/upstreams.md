## legacy 平台是什么

真实在跑的电表 / 终端自动化测试平台:659 条条款用例(全 `test_M_*`)、六套协议(gRPC + protobuf)、OBIS 点表、台架操作对象、固件 hex 校验、虚拟表、OCR。

**不是同一个技术栈**:它的设备访问全部经过 gRPC 台架服务,而不是串口/TCP 字节流。

## 为什么整仓并入会毁掉这个项目

- 1596 个文件、999 个 Python 文件、22 个 dll、9 个 pdb
- 平铺脚本结构,没有领域层,业务规则与协议字节混在用例里
- 自带 `7za.exe`、`test.log`(218KB)、`test.html`、`__pycache__`、`.pytest_cache`

并进来会把这些直接压到我们的 `domain / drivers / transport / composition` 之上,分层就没了。

## 它替我们验证过的判断

这些不是我们拍脑袋定的,旧平台已经用真实代价证明了:

- **按物理量名取数**可行:`read_obis('正向有功总电能:value')`
- **点表要集中声明**:OBIS 映射一处定义,用例不写地址
- **周边设备是一等公民**:台架、摄像头、脉冲计数都是必须被控制的对象,不是夹具细节
- **用例必须有编号与条款**才能被引用
- ~~用例参数与用例逻辑分离:每条用例配 `.py.cfg`~~ —— **实测不成立**:659 条用例里只有 101 条有 `.py.cfg`(15%),且样例内容是 `127.0.0.1:66666,127.0.0.1:55555`,是台架地址而不是阈值。阈值实际散在调用参数与函数默认值里(如走字判定的 `fPercent=1`),所以「矩阵化」只能作为**需求方向**佐证,不能当作上游已验证的做法

## 2. 架构上的根本差异

上游是**工单执行器**,本项目是**断言规则库**。这一条决定了其余所有差异。

| | 上游 | 本项目 |
|---|---|---|

| 设备怎么访问 | 全部经 gRPC 台架服务:`Control('127.0.0.1:66666', '127.0.0.1:55555', ...)` 写在各用例文件里 | 串口 / TCP / SSH 字节流,`transport/` 三个实现互不知道对方存在 |

| 一条用例覆盖几台设备 | 一个用例文件里 new 出十几台台架对象,自己编排 | 契约层自动按类型展开;跨设备联动走 `tests_scenario/` 并落 `scenario-*.json` |

## 4. 迁移的判断标准

不要以"上游怎么写"为验收标准。两条硬标准:

1. **同一条条款在本项目里必须能用判据集 + 读数键表达** —— 表达不了,说明缺的是读量能力(点表/协议),不是用例代码。
2. **迁移后改阈值只碰 yaml** —— 如果还要改 Python,说明阈值又硬编码回用例里了。

反过来,以下不迁:工单对接、`taskId` 传递、用例内硬编码 IP、`oper_object` 的类名、四个巨型 dict 的原始形状。

## 5. 硬标准 1 的实测结论(拆了一条真实条款)

拿 `M_00_00_01_000002_01`(进入/退出工厂模式 + 计量模式读写 + 改密码 + 合相双向走字误差,977 行)按「判据集 + 读数键 + 场景步骤」拆,结论是**只对读数型条款成立**。

659 条用例的动作构成(实测):

| 动作 | 条款数 | 占比 |
|---|---|---|
| 含 `universalSet`(向被测设备**写**参数) | **542** | **82%** |
| 含 `runWord`(走字 + 误差判定) | 29 | 4% |
| 只读不写(有 `universal_read` 无 `universalSet`) | 32 | 5% |
| 含事件 / 冻结关键词 | 70 | 11% |

**平台缺三样东西,缺一样就迁不了对应的一批条款:**

1. **写原语** —— 驱动目前只有 `read_all` / `read`。要让场景"设定被测设备参数",需要 `write(point, value)` + 点表项标 `writable`。挡在前面的是 542 条。
2. **派生量** —— 误差 =(被测增量 − 标准表增量)/ 标准表增量,跨两台设备求差。判据集的 `quantity` 现在必须是**单台设备**的读数键。
3. **相等判定** —— "写 F001,读回应等于 F001"是值相等,不是区间。判据集只有 `min` / `max` / `gt` / `lt`,没有 `equals`。

顺序应该是:先补这三样 → 再拆用例。反过来先拆,会写出大量 `assert` 塞在场景函数里,把 ADR 0005 刚关上的那扇门重新打开。

## 1. 台架 14 个量

我们的 14 个读数键 = `configs/devices.yaml` 里 `grid_simulator_3ph` 的点表(`Ua..Ic`、`θa..θc`、
`QUaUb`、`QUaUc`、`Fre`、`接线方式`、`MeterConst`)。上游不是"14 个寄存器",而是两层:

```
条款里写        台下给台架的两个数
Ua=Un      →   fUe = 230(V)        + fRangeUa = 100(%)
Ia=Ib      →   fIe = 5(A)          + fRangeIb = 100(%)
θa=0°      →   fAngleUaIa = 0(°)
Fre=Hz     →   fHz = 50(Hz)
```

所以"单位"要分两栏看:物理单位是 V/A/°/Hz,而**电压电流在台架上永远是"额定值 + 百分比"两个数**
(`oper_object/runtime.py:87-89` 的 docstring:`fUe=额定电压V`、`fRangeUa：A相电压百分比`)。
把 `fRangeUa=100` 当成 100V 是这一块最容易犯的错。

| 我们的量 | 上游参数 | 单位 | 换算 | 整数 | 出处 |
|---|---|---|---|---|---|
| Ua / Ub / Uc | fUe × fRangeUa/b/c | V | 额定电压 × 相电压百分比 / 100 | 否 | `runtime.py:87-88`、`pypack/bench/parameter.py:14-16` |
| Ia / Ib / Ic | fIe × fRangeIa/b/c | A | 额定电流 × 相电流百分比 / 100 | 否 | `runtime.py:87,89`、`parameter.py:18-20` |
| θa / θb / θc | fAngleUaIa/b/c | ° | 直给 | 是 | `runtime.py:68`、`parameter.py:22-24` |
| QUaUb / QUaUc | fAngleUaUb / fAngleUaUc | ° | 直给 | 是 | `deskParam.py:10`、`globalvar.py:12`、`parameter.py:25-26` |
| Fre | fHz | Hz | 直给 | **两处声明矛盾**(读侧 int / 写侧 float) | `runtime.py:60`、`parameter.py:28`、`parameter_tx.py:16` |
| 接线方式 | bConectionType | 枚举 | 见 §3 | 是 | `runtime.py:59`、`tests/param.py:27,69` |
| MeterConst | fMeterConst | **没写明** | 直给(脉冲常数) | **两处声明矛盾** | `globalvar.py:13`、`parameter_tx.py:23`、`tests/param.py:21` |

三处"不落值"的地方是故意的,不是没查:`Fre` 与 `MeterConst` 的上游两处声明互相矛盾(int vs float
/ 有无单位),填一个就是替上游选边;`MeterConst` 的单位(`imp/kWh` 还是别的)上游一个字都没写。
**量程**同样只落了能落的:百分比那一档上游只给默认值(`fRangeUa=100`、`setBottomEnergy` 里
`fRangeIa=200`),上限要台架手册。逐条细节与行号在 `bench_quantities.yaml` 里。

条款里的符号值(`Ua=Un` / `Fre=Hz`)在上游是五个全局量:`Un=230`、`In=5`、`Imax=70`、`Hz=50`、
`C=1000`(`tests/param.py:13-21`)。
**一处要留意**:本仓 `configs/devices.yaml` 的台架前置写的是 220V,上游这套用例是 230V。
两个都对(不同被试品),本票不改 42 的清单,只在 `bench_quantities.yaml` 的 `symbolic_values.Un.note` 里记着。

## 2. 上游 docstring 有个洞(票面写错了)

票面说"出处指到 `oper_object/runtime.py` 的 `runWord` docstring"。实测:`runWord` 的 docstring
(`runtime.py:66-68`)只写了电流百分比与压流角,**没写** `fUe` / `fRangeUa` / `fHz` 的单位。
那三个数只写在同文件的 `setBottomEnergy` docstring(`runtime.py:87-89`),参数集与 `runWord` 相同。
所以本票的出处引的是 87-89,不是 66-68 —— 引 66-68 会得到一个"看着有出处、其实那行没这句话"的假绿。

## 3. 接线方式:上游有**两套**整数,中文名是我们的

| 编码 | 在哪 | 值域 | 上游给了什么 |
|---|---|---|---|
| `Ctype` | 用例层 `tests/param.py:27` | 0 / 5 / 9 / 10 / 51 / 52 / 53 / 54 / 91 | 只有整数;元件数由 `param.py:69` 的 `CalPhaseNum` 算出来 |
| `MeterTypes` | 台架协议层 `pypack/pyproto/hxp3001c/typedef/metertypes.py:17-25` | 0x30–0x39 | 整数 **+ 英文名**(`M_3p4w_watt` 这种) |

两套之间**没有对照表**:上游没有任何一处把 `Ctype=5` 映射到 `MeterTypes.M_3p4w_watt`。别自己接。

`Ctype` 那一半只给得出元件数(`3` / `2` / `1`),给不出"这是几相几线":2 元件的整数有五个
(`0/10/51/53/54`),"三相三线"和"三相四线两元件"都落在 2 元件上,上游没说哪个是哪个。
`MeterTypes` 那一半因为英文名自带 `3p3w` / `3p4w` / `1p2w`,反而是上游唯一能读出接线方式的地方。

**中文名是本仓定义。** 上游全仓 `3P4W` / `三相四线` / `三相三线` 0 命中,所以 `names_zh` 那几行的
`source` 逐字写 `本仓定义(上游无中文名)`,校验脚本会盯着这一句(有人给它编个上游出处就红)。

`13通信` 里接线方式只出现一个取值:`与表型一致`(138 次)。它不是常数,是"按被测型号接",
所以 `params.yaml` 里给它 `null` 而不是某个整数 —— `null` 在报表里是一行看得见的缺口,
填个 0 就把缺口藏了(而 0 恰好是 `Ctype` 的一个真取值)。

表自己也有"接线方式":DLMS `0-0:96.2.241.255`(`obisDict.py:9766`,类 1、长度 2、unsigned)。
**这是表的点,不是台架的 `Ctype`,也不是 Modbus 寄存器。** 三者是三套编号。

```

# 没设 --upstream / UPSTREAM_DIR 时:skip(退出码 0)并说明为什么

```

它做五类断言(逐行 111 条 + 反向断言 25 条):

1. `source: "<相对路径>:<行号>"` 那一行必须含 `expect` —— **行号错一位就红**;
2. `ctypes` 每行按 `(Ctype==<取值>)*<元件数>` 去 `param.py:69` 比对 —— **元件数写错也红**;
3. `name_needle`(条款里的写法)在五份上游字典里必须 0 命中 —— 上游补上了就红,提醒重新提取;
4. 中文名那半张表的 `source` 必须逐字是 `本仓定义(上游无中文名)` —— 给它编个上游出处就红;
5. `writes.yaml` 的 `expect` **不在 yaml 里**:脚本用记录自己的 DI / c / 长度 / 类型拼出上游那一行
   该有的内容再去比对 —— 改 yaml 里任何一位都红。另加两条结构断言:图例的 `digits` 必须等于
   `2 × length`(两个数来自上游两处,抄错一处就不相等);重复的 DI 键直接报错(yaml 默认后者
   覆盖前者,会让被覆盖的那条连检查都不跑 —— 实测踩过一次 110 条全绿的假绿)。

路径不写死:上游不并入本仓,所以别人 clone 下来没设环境变量时它 skip 并说清楚要指到哪。
