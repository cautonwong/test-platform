# PRD:任务驱动的端到端测试平台(EdgeC 解决方案)

Status: ready-for-agent
Type: spec

## Problem Statement

EdgeC 是 monorepo,**被测对象是整个解决方案**:`cmd/` 下的 8 个产品(dcu / iems / hems / evse / sg / smart_box / edge_mcp_server)是边缘网关,它们采集周边设备(电表、逆变器、电池、台架)再向上报送。今天的问题有四层:

1. **产品侧的验证只在虚拟总线上** —— 现有内部测试工具用虚拟总线驱动产品,能验证编排逻辑,但**无法验证"真实报文、真实故障、真实时序"下的行为**:设备不回、坏 CRC、慢应答、中途断链,这些今天没人系统性验过。
2. **结论不可审计** —— 产品出问题时要翻日志;没有"这条结论依据哪条标准条款、读了哪一帧、超出多少"的可追溯记录。
3. **资产无法管理** —— 目标是几千台设备实例、上万条测试项、几十个场景。今天没有统一目录:不知道"这个型号有哪些测试项覆盖""这条标准条款有没有人测""这个型号在 CI 上跑不跑得起来"。
4. **验收靠人** —— 一次测试跑完,过没过取决于谁看日志;没有可交给验收方的结论,也没有 CI 门。

测试工程师要写一条用例,得同时理解协议字节、设备语义、证据格式;产品开发者改了接口,不知道哪些用例会红。

## Solution

把测试平台定位为**任务驱动的端到端测试执行器**,围绕两条工作流:

**工作流 1(扩展 → 用例 → 场景 → 入库)**:新增一类设备/一个协议/一个模拟器,都只加资产、不改平台骨架;测试项用 pytest 代码写(遵 ADR-0002),场景用例用显式参与方声明(遵 ADR-0005);写完由目录自动收进资产目录。

**工作流 2(建任务 → 筛选 → 跑 → 报告)**:一次测试 = 一个**测试任务**。任务声明"测哪个产品、起什么命令、用哪份设备清单、选哪些用例、明确不测什么"。平台启动产品进程、拉起模拟周边设备、跑用例、落证据,产出**四档结论**的报告;CI 由一个独立 gate job 判红绿。

资产三分:**平台**(执行引擎,以 npm 包分发)、**公共数据**(周边设备型号库/判据集/标准条款清单,以 npm 包分发)、**产品用例与场景**(留在 monorepo,跟产品一起演进)。

## User Stories

### 测试工程师:写用例

1. 作为测试工程师,我想要新增一台周边设备时只改清单,以便不用碰任何 Python 代码。
2. 作为测试工程师,我想要新增一个同协议的设备型号时只写点表,以便型号差异不散进代码。
3. 作为测试工程师,我想要写一条一致性测试项时只写读数键与断言(约 4 行),以便把精力放在判据上而不是协议字节上。
4. 作为测试工程师,我想要一条用例自动对清单里每台同型号设备各跑一次,以便加设备不用加用例。
5. 作为测试工程师,我想要声明"这条用例依赖某能力",以便设备缺该能力时自动跳过而不是报失败。
6. 作为测试工程师,我想要写跨设备场景时显式点名参与方与 role,以便结论能归到设备或台架。
7. 作为测试工程师,我想要在场景中途直接设定模拟设备的读数(比如把电量设成 1234),以便验证产品对特定数据的反应。
8. 作为测试工程师,我想要这个"设定读数"的动作留在证据里,以便事后知道是谁设的值。
9. 作为测试工程师,我想要引用标准条款时从受控清单里选,以便拼错时当场报错而不是静默记成另一条。
10. 作为测试工程师,我想要中途让产品重启(冷启动类条款),以便验证重启后的行为,而不用另建一条任务。

### 产品开发者:接产品

11. 作为产品开发者,我想要在 monorepo 里为我的产品维护自己的测试任务与用例,以便改接口时同一个 PR 里改用例。
12. 作为产品开发者,我想要任务里写启动命令(含参数与占位符),以便平台按我的方式起产品,而不强迫我改接口。
13. 作为产品开发者,我想要平台自动分配端口与 UDS 路径并传给我的产品,以便并行跑多个任务不会撞端口。
14. 作为产品开发者,我想要平台把实际使用的命令行写进证据,以便本地能复现同一轮。
15. 作为产品开发者,我想要产品自己退出(崩溃)时被判为"产品不合格",以便崩溃不会被当成环境问题糊过去。
16. 作为产品开发者,我想要平台主动杀掉产品时不被记成故障,以便收尾不会污染结论。
17. 作为产品开发者,我想要产品起不来(二进制缺失/参数错)被判为"平台错误"并指出原因,以便我知道是配置问题不是我的代码问题。

### 平台维护者:扩展平台

18. 作为平台维护者,我想要新增一个协议只是加一个编解码模块 + 注册一行,以便协议扩张不牵动骨架。
19. 作为平台维护者,我想要新增一个模拟器只是加一个工厂并声明它支持哪些故障注入,以便 CI 能判断某型号可不可跑。
20. 作为平台维护者,我想要模拟器只做"点表可读写 + 故障注入 + 数据注入",不做设备业务行为仿真,以便不用维护一套"假电表的行为规范"。
21. 作为平台维护者,我想要同一个型号的进程内模拟器与独立进程模拟器共用同一份应答数据与编解码,以便两者不会漂开。
22. 作为平台维护者,我想要平台的测试缝只有少数几个(一个集成缝 + 两个纯函数缝),以便功能演进时测试不会跟不过来。

### 测试工程师:建任务与跑

23. 作为测试工程师,我想要用一个任务文件声明"这次测什么"(产品 + 设备清单 + 用例筛选),以便下个月还能原样复现同一批。
24. 作为测试工程师,我想要在任务里显式声明"本次不测什么"及理由,以便"没测"是申报而不是遗漏。
25. 作为测试工程师,我想要报告告诉我"这一轮的范围是多少条条款",以便我知道通过率的分母是什么。
26. 作为测试工程师,我想要未测分成"申报内(灰)"与"申报外(红)"两栏,以便一眼看出有没有漏测。
27. 作为测试工程师,我想要通过率分"设备级"和"场景级"两栏,以便不会被一个合成数字掩盖问题。
28. 作为测试工程师,我想要报告里不合格项写清"哪台设备、哪条条款、超出多少",以便我知道从哪改。

### 验收方与 CI

29. 作为验收方,我想要报告首行只给四档结论(合格 / 不合格 / 测试无效 / 未完成),以便不用自己读证据判过没过。
30. 作为验收方,我想要报告包含"依据哪条标准条款"和证据指针,以便结论可追溯。
31. 作为 CI,我想要一个任务跑在一个 job 里,以便失败互不阻塞且能并行。
32. 作为 CI,我想要一个独立的 gate job 汇总所有任务结论并决定红绿,以便 GitHub 的二元结论不吞掉四档语义。
33. 作为 CI,我想要"测试无效"在 CI 里判红并指向平台,以便平台自身的问题不会被忽略。
34. 作为 CI,我想要报告作为 artifact 保留而证据只上传失败部分,以便产物可控。
35. 作为 CI,我想要 PR 只跑指定的任务、nightly 跑全量,以便 PR 反馈够快而全量仍然覆盖。

### 资产管理者

36. 作为资产管理者,我想要一份从代码与清单生成的资产目录,以便回答"这个型号有哪些用例覆盖""这条条款有没有人测"。
37. 作为资产管理者,我想要目录列出缺口(型号缺判据、能力不在点表、型号没有模拟器、条款零覆盖),以便知道该补什么。
38. 作为资产管理者,我想要目录在加载期校验用例编号全局唯一,以便 `--select` 子集跑时也不会漏掉重复编号。
39. 作为资产管理者,我想要目录告诉我某型号在 CI 上可不可跑(有没有模拟器、支持哪些故障注入),以便排任务时不踩空。
40. 作为资产管理者,我想要产品清单只能按"包名 + 型号 id"引用公共型号库,以便点表不会被复制成多份。

## Implementation Decisions

### 数据模型(四个新资产)

- **测试任务**:`id`、`product`(仅身份与追踪)、`launch`(含 `${PORT}` / `${UDS}` 占位符的命令行)、`devices`(设备清单引用)、`select`(用例筛选)、`not_tested`(申报不测 + 枚举理由)、`scope_note`。
- **测试报告**:两产物 —— 人读的摘要与机器读的 `summary.json`;后者含结论、两栏通过率、不合格与未测清单、`runtime`(产品启动/首个读数/总耗时)、`env`(commit、平台版本、产品二进制 sha256、模拟器版本)。
- **资产目录**:由清单 + 注册表 + 测试文件**生成**,不手改;含资产清单、引用关系、缺口列表。
- **标准条款清单**:受控集合,`id → 标准 / 编号 / 标题`;用例引用 `id`,未知 `id` 在收集期报错。

### 进程生命周期

- 一轮一个产品进程;平台负责启动、就绪等待、收尾。
- 就绪等待只发生在连接阶段(可配超时与间隔),**等待时长进证据**;场景层不做"轮询到条件"(遵 ADR-0005)。
- 进程死亡按死因分类:**自己退出**(非零退出码/信号)= 产品不合格;**平台主动终止**= 不计失败;**起不来**= 平台错误。分类依据是平台自己是否发起过终止。
- 崩溃后**不自动重启**;本轮剩余用例记为测试无效,并在报告里与崩溃本身分开陈述。
- 提供显式的"重启产品"动作给需要冷启动的用例;重启点写入证据。
- 产品的 stdout/stderr 落盘进证据。

### 端口与路径分配

- 任务里写占位符,不写具体数字;平台分配空闲值并替换,实际命令行进证据。
- UDS 路径带任务 id 与进程号,避免残留冲突。

### 模拟器

- 保真度上限:**点表可读写 + 故障注入(超时/坏 CRC/慢/断链)+ 数据注入**;**不做设备业务行为仿真**;需要行为仿真的条款列入"平台不支持"。
- 数据注入两个入口:**初值进清单**(声明式,随任务)"、**场景中途 `inject()`**(命令式,写入证据,且**不得替代写路径** —— 测"产品能否写设备"必须走协议写)。
- 注入点必须是该型号点表里已声明的量,拼错当场报错。
- 每个模拟器声明**支持的故障注入种类**,目录据此算出型号的 CI 可跑性。
- 同型号的进程内模拟器与独立进程模拟器共用同一份应答数据与编解码,并有逐字节对照守卫。

### 范围与分母

- 平台不承担调度:一个任务即一个范围;PR/nightly 的差别只是跑不同任务。
- 分母 = `select ∩ 适用矩阵` 命中的条款集合,**写进报告**。
- 未测分两类:申报内(灰,理由必须来自枚举:平台不支持/设备缺能力/人工步骤/已知缺陷跳过)、**申报外(红)**。
- 申报引用了不存在的条款/型号 → 任务加载期报错。

### 报告与结论

- 四档结论:**合格 / 不合格 / 测试无效 / 未完成**;**禁止出现"通过但存在申报外未测"**。
- 通过率**分两栏**:设备级 N/M、场景级 N/M;任务结论取两栏最差。
- 场景失败必须标注归属(设备 / 台架 / 平台),不得合并成一句"场景失败"。
- 报告只进 CI artifact(默认 90 天),不进版本库;证据默认只上传失败/无效用例涉及的设备,全量证据需显式开启。

### CI 形态

- 一任务一 job(矩阵,`fail-fast: false`);产品二进制由独立构建 job 产出并以 artifact 传递。
- **独立 gate job** 汇总所有任务的 `summary.json`,按四档规则给出最终红绿:任一不合格/测试无效/未完成/平台错误 → 红。
- CI 里"测试无效"= 红,报告首行声明"平台问题,不是产品",并给三类排查提示(模拟器未起、端口未分配、产品未就绪)。
- 平台自身以 npm 包分发,monorepo 锁版本;**加协议 = 平台改 + 发版 + monorepo 升版**(已确认接受);平台对协议扩展自动发预发布版,避免本地分叉。
- 公共数据(型号库/判据集/条款清单)以 npm 包分发;产品用例、场景留在 monorepo;公共包**只装数据不装用例逻辑**。

### 平台内部形状

- 新增职责模块:**任务执行器**(解析任务、起停进程、编排)、**报告生成器**(证据 → 摘要 + `summary.json`)、**门禁判定**(报告 → 退出码)、**资产目录生成器**。
- 只新增一个协议:**Modbus TCP(MBAP)**,作为第一个为 EdgeC 产品服务的协议;其编解码是纯函数,模拟从站按"帧格式"参数化(同一份实现产出 RTU 或 MBAP)。
- 既有骨架不改:设备/型号/点表/判据集/拓扑/证据/四类归因/并行分组全部复用。

## Testing Decisions

**什么算好测试**:只断言外部可观察行为 —— 退出码、报告字段、证据里的帧字节、目录的缺口清单;不断言内部函数调用顺序、不 monkeypatch 私有方法。

**测试缝(3 个新缝 + 1 个复用缝)**:

1. **任务执行缝(最高)**:一个真任务文件 + 一个"假产品"子进程(小脚本:监听端口、按 Modbus 对话、可配置崩溃/不启动/慢启动),配一个真 socket 的模拟从站。一次覆盖:任务解析 → 端口替换 → 进程启动 → 就绪等待 → 产品读值 → 断言 → 证据 → 报告 → 退出码。**该缝必须覆盖 Modbus TCP(MBAP)**,因为那是 EdgeC 产品的真实链路形态。
2. **门禁缝(纯函数)**:一批 `summary.json` → 退出码;覆盖四档组合与"申报外未测"。
3. **目录缝(纯函数)**:一个 fixture 目录树 → 目录产物;覆盖八项引用完整性与缺口输出、编号全局唯一(独立于收集期筛选)。
4. **复用既有缝**:协议编解码、清单校验、模拟器读写与故障注入、数据注入 —— 沿用现有单元缝与"真 socket 模拟从站"用例,只加用例不开新缝。

**先例**:现有 `tests/test_mock_meter_end_to_end.py`(真 socket + 子进程 + 故障注入)就是缝 1 的形状先例;`tests_unit/test_attribution.py` 是缝 2/3 的纯函数先例;`tests_unit/test_manifest_*.py` 是装配期校验的先例。

**变异要求**:每个新增守卫要能失败 —— 行号改错、型号参数缺失、模拟器能力声明被删、gate 规则被削弱,对应用例必须红(改造一处即红的用例要有)。

## Out of Scope

- **多产品协同测试**(一个任务起多个产品进程 + 共享总线):已确认先只做"一个产品 + 模拟周边设备"。
- **影响面分析**(改哪个文件 → 该跑哪些任务):平台不承担调度。
- **趋势库 / 与上次任务对比**:等有人真的问再加。
- **设备业务行为仿真**(电量累积、状态机、告警时序):明确不承诺。
- **协议面扩张**:除 Modbus TCP 外(DL/T698、DLMS、IEC101/104、CAN)不在本期。
- **真实台架验收**:本期只有模拟器路径;真机首跑另立。
- **平台进 monorepo 子目录**:已改为 npm 分发,不在本期迁移代码。

## Further Notes

- **术语**:沿用项目词汇(被测设备 / 周边设备 / 设备实例 / 设备类型 / 能力 / 点表 / 一致性测试 / 场景测试 / 测试层 / 测试项 / 不变量 / 判据集 / 证据 / 归因)。
- **已定 ADR 不可翻案**:测试项用 pytest 代码写(ADR-0002);场景层是代码 + 显式参与方,不支持分支/循环/并发(ADR-0005);台架前置与被观测变量的区分(ADR-0006)。本 spec 新增"任务/报告/目录"三个概念,不改这三条。
- **已知风险**:①平台发版频率与协议扩张速度会互相牵制,靠自动预发布版缓解;②"CI 里测试无效 = 红"要求模拟器与进程管理足够稳,否则 PR 会周期性变红,治理方式是修模拟器而不是摘任务;③报告的两栏通过率在只有少量场景时会显得不平衡,是预期现象。
- **第一个里程碑建议**:任务执行缝(假产品 + MBAP 模拟从站)+ 门禁缝,让"跑一个任务 → 出四档报告 → gate 判红绿"闭环;目录与公共包下一期。
