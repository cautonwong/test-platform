# 14 闸门偶发:端口被抢 + 产品崩了还被重试

Status: resolved
Priority: P0(它护的是"平台能不能说清自己为什么停")

## 由来

票 11 的 20 轮计数里,`test_task_runner.py` 一组 4 条在一次闸门里 4 failed、重跑全绿。
现场:43 份 `task.json` 显示**0.8 秒内 4 个 worker 全部端口耗尽**,随后逐步中招。

## 根因(实测)

1. 平台用 `bind(0)` 从系统临时池取端口 → `probe.close()` → 产品启动(150–300ms 窗口)→ 别的进程 `bind(0)` 分到同一端口 → 产品 `10013`
2. 重试拿到的新端口来自**同一个共享池、同一个时间窗** → 3 次全丢 → 平台错误
3. 平台探针**不带 `SO_REUSEADDR`**,自己把端口留成"别人带 `SO_REUSEADDR` 就回 10013"的状态 —— **平台自己的验证成了丢端口的原因**
4. 判序反了:先判端口后判产品死活 → **产品崩了还被换端口重试**

## 修法

- 端口从**平台段 `20000-31999`** 顺序取,不与 Windows 49152+ / Linux 32768+ 重叠;整段不可用 = 平台错误(列端口 + "不是产品不合格")
- 探针带 `SO_REUSEADDR`;起点取 **8 字节熵**(2 字节对 12000 取模偏向低段,实测 27135/27136/27137 连丢)
- **判序写死**:产品已死 → 一律不重试;只有「产品没起来 + 端口不可用」才重试
- `port_retry` 事件带 `reason`,**闭集**:`端口他人不可用` / `产品 stderr 自报 bind 失败`
- `TESTPLATFORM_PORT_RANGE` 与系统分配区重叠 → **加载期报错**(不静默照用)
