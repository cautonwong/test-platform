# 02c MBAP 事务号只发不验:迟到应答会被当成当前应答

Status: resolved
Type: task
Blocked by: None — 小改动,与 01 不撞文件

**What to build:** MBAP 头里的事务号是用来把「请求」和「应答」对上的。现在只发不验:请求按 `_next()` 递增,应答解析时事务号被丢弃(`_split` 的返回值里第一个就是它,但 `parse_read_response` 用 `_` 忽略了),于是**任何事务号的应答都被接受**。

## 实测

```python
请求事务号: 1 | 应答事务号: 999
解析结果: 0001e240        ← 事务号对不上仍然被接受
```

## 为什么算缺陷而不是"以后再补"

具体失效场景:上一条请求超时,应答迟到;平台发下一条请求,先读到的是**迟到的旧应答**。因为它来自同一从站、同一功能码、长度也对,单元号/功能码/字节数三项检查全部通过 —— **事务号是唯一能发现它的手段**。结果是一条"看着完全正常"的错位读数,后续判据基于错误的值给出合格/不合格。

这和既有设计里"迟到应答会让整帧错位"(串口换向前清输入缓冲)是同一类问题,只是 MBAP 有原生手段却没用上。

## 期望

1. 请求侧记住"当前未完成请求的事务号"(不是简单 +1 就忘)
2. 应答解析时比对;**不匹配 → 抛可辨认的错误**,消息里给出期望事务号、实际事务号,并提示"这是上一条请求的迟到应答"
3. 与现有异常区分:这不是超时(`TimeoutError`)、不是断链(`ConnectionError`)、也不是从站拒绝(`SlaveExceptionResponse`),是**应答错配**
4. **不要**自动重发或忽略后重试 —— 先让它红,重试是后续独立决定
