# 12 `_free_port()` 分配后放掉再 bind:CI 里会偶发"端口已被占用"

Status: resolved
Type: task
Blocked by: None — 与 04/06 不撞文件

**What to build:** 任务执行器分配端口的方式是"探一个空闲端口 → 关掉 → 把端口号写进产品命令行让产品自己 bind"。中间有一个窗口:探完到产品 bind 之间,别的进程(或同 runner 上另一个 job、或上一轮没死透的进程)**可以抢走它**。

## 为什么现在开票

票 11 已经出现"组合闸门 1/6 红"的现象,而这类红的候选原因之一就是这个窗口。我们定过:**CI 里"测试无效"= 红,没有真台架抖动这个合法来源** —— 所以偶发红必须查清,不能攒到 09/10 接线时再算到"CI 不稳"头上。

代码里已标 `shortcut:` 并写了升级条件(产品支持继承监听句柄)。**这不改变它是个真实竞态**,只是说明当初的取舍。

## 期望(按代价从小到大)

1. **产品启动失败时重试**:bind 失败(端口被占)时,重新分配一次并重启产品,最多 3 次;每次记进证据(`{"kind":"port_retry","attempt":N,"port":...}`)
2. 分配端口时**避开**"刚被别的分配用过的"号段(简单的滑动窗口,避免两个并发任务撞同一号)
3. 长期:产品支持继承监听句柄时,由平台 bind 后把 fd 传下去(那时这个竞态从根上消失)

**先做 1**,它把"偶发红"变成"自动重试且留痕";2/3 视 CI 实测再定。

## 验收

- [x] 端口被占时任务不直接失败,而是重试(≤3 次),证据里能看到重试记录
- [x] 3 次都失败 → 结论是**平台错误**(不是产品不合格),消息点明占用端口
- [x] 有对应用例:先占住平台要分配的端口(或注入一次失败),断言重试发生
- [x] 基线不回归,差值可解释
