# 29 块读降级不记忆:有空洞的点表上,合并比逐点更慢,而且每轮都付一次

Status: resolved
Type: task
Blocked by: None

**What to build:** `1b99a93` 让块读被异常应答拒掉时降级为逐点重试 —— 正确性没问题,失败也给得具体。但**降级不记忆**:下一次 `read_all()` 仍然先试合并的块,被拒,再逐点。真实电表的寄存器地址几乎总有空洞,所以这不是罕见的兜底路径,而是**稳态**。

## 现状(实测)

`tests/test_meter.py:588` 那条用例自己把帧序列打出来了:

```
(1, 0x03, 0, 3)   # 先试合并的块(地址 0 起 3 个),被异常码 03 拒
(1, 0x03, 0, 1)   # 降级:逐点重试
(1, 0x03, 2, 1)
```

两个点 → **3 次往返**;不合并则 2 次。也就是说:当点表里有未实现的空洞地址时,合并块读把 2 次往返变成 3 次,并且每次 `read_all()` 都这样。

`MAX_GAP_TO_MERGE = 10` 的取舍注释只算了"空隙占应答字节与一次往返",没算**被拒后重试的代价** —— 而后者由从站实现决定,不看我们的意愿。`_gap_model` 里地址 1 未实现就是最常见的真机情形(电表只实现点表里那些寄存器)。

## 影响

1. **性能**:稳态下每个读周期多一次往返。20 ms RTT、20 个点、5 秒一周期 → 每周期多 20ms,一天多约 350 秒的有效等待。
2. **证据**:每轮写一条 `kind: batch_fallback`(`evidence.py:291`)。一轮 1440 次读就是 1440 条降级记录 —— 现场看报告会以为设备一直在报异常。
3. **排障误导**:读者会把"稳态的空洞"读成"设备偶发异常应答"。

## 期望

二选一(推荐 A):

**A. 会话内记住被拒的块,收缩后不再试**
- 以 `(slave, function, address, count)` 或更粗的"块区间被拒过"为键,记在驱动实例上
- 下次规划时把这些块拆细:**只合并真正相邻的寄存器**(gap = 0),空隙不再扫
- 证据里只在**第一次**降级时写 `batch_fallback`,后续不再刷屏;读周期的帧数回到 N

**B. 合并默认不跨空隙,跨空隙要显式开**
- `MAX_GAP_TO_MERGE` 改成 0(只看连续区间),需要跨空隙的型号在清单里声明(如 `merge_gaps: true`)
- 好处:默认不做有风险的合并;坏处:同一型号两种行为,清单变复杂

## 不做

- 不做"探测一次全局关闭块读" —— 有的设备只是某几个地址没实现,其余仍可合并
- 不因为降级就把结论变红:降级是性能事件,不是设备不合格
