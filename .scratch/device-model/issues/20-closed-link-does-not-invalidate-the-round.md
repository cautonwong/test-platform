# 20 断链还没走到"测试无效":收帧期的 closed 没有归属

Status: resolved
Type: task
Blocked by: 需要先定一个产品口径(见下),不是纯实现

**要做什么:**`issue/18` 已经把"断链"和"设备不回"在底层分开了(证据里 `closed` / `timeout`),但**这个区分还没有被上层用起来**:收帧阶段遇到 `closed` 时,没有任何地方把它转成"测试无效"。也就是说,断链今天仍然会被当成用例失败(设备不合格),只是证据里多了一个 `closed` 可查。

## 现状

- `connect_support()` 只覆盖**连接阶段**的周边设备故障 → `SupportEquipmentFault` → 测试层转 `skip("测试无效: …")`。
- 收帧阶段的 `ConnectionError`(`closed`)在任何层都没有被转换成"测试无效"。
- 另外 `gateway_transport.py` 里"网关转发失败"抛的也是 `ConnectionError`,现在一并记成 `closed`。语义上属于"链路不在",但如果你希望它能和"对端 FIN"区分,需要另立一个异常类型。

## 先定口径(这是本票的阻塞点)

周边设备(台架 / 终端 / 网关)在**收帧阶段**断链时,应该是:

- **(A) 立即判整轮无效**:整轮结论作废,后面的用例也不跑。简单、保守,但在长轮次里会浪费已完成的测试。
- **(B) 只有确实用到它时才判无效**:精确,但需要"哪条用例依赖哪台周边设备"的声明 —— 这份声明目前刻意没做(属场景层的设备依赖声明,见 `tickets.md` 票 4 的已知限制)。
- **(C) 本轮继续,但在证据与汇总里标记"该轮存在断链,结论需复核"** ← 用户选定:不需要依赖声明,代价是结论不是二元的。

**建议 (C)**:它是唯一不需要先建依赖声明、又不会把台架问题算到设备头上的做法。(A) 会在长轮次里过度作废,(B) 依赖一份今天还不该猜的声明。

## 验收(口径定了之后再落)

- [x] 周边设备在收帧阶段断链时,结论按选定口径处理(不是"设备不合格")
- [x] 被测设备自身断链(它是 DUT,链路就是它的一部分)仍按设备不合格处理 —— 两者不能混
- [x] 证据与汇总里能看出"这一轮存在断链"
- [x] `gateway_transport` 的 `ConnectionError` 语义与"对端 FIN"是否需要区分,有明确结论并写进注释

## Comments

- 2026-10-21 出票依据:`issue/18` 的交付报告自己指出的残余("收帧阶段的 closed 目前没有任何地方转成测试无效")。我没有让它硬造,因为这牵涉产品口径而不是实现细节。

- 2026-10-21 口径定为经第三条路落地:收帧期 `closed` 按设备清单里的 `role` 分流,不走"把 failed 改写成 passed",也不把台架问题记在设备头上。周边设备断链 → `SupportLinkLost` → 测试层唯一一处转成 `skip("测试无效: …")`(沿用票 4 的 `TEST_INVALID_PREFIX`),整轮照常跑完、退出码不变;被测设备断链原样上抛,仍按设备不合格处理。归属只看 `role`,不看异常类型。
- 三处痕迹:证据里 `kind: link_lost`(设备 id / 时间 / 收发哪一侧 / 失败种类 `closed`)、终端小节「本轮存在断链 —— 结论需复核」(次数 + 设备 id + round-status 路径)、`evidence/<会话>/round-status.json`(`verdict`: `needs-review` / `clean` + `link_lost` 列表)。没有断链时这份文件照样写、列表为空,CI 不必解析终端文本。
- `gateway_transport` 结论:沿用 `ConnectionError`(证据记 `closed`),不另立"对端 FIN"类型。理由:SSH 会话断了与 agent 返回非零,上层结论一样(台架链路不在 = 本次测试无效);要分开得先让 agent 返回结构化错误码,今天只有退出码 + stderr。已知失真写进模块注释:agent 自己等超时也是非零退出,所以这一路径会把"设备不回"报成 `closed`;等 agent 能区分"没人答"与"链路不在"两种错误码时再拆。
