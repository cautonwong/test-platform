Blocked by: 36(人工步骤落点)

**What to build:** `docs/表计功能测试用例V3.2.1（20241108F）.xlsx` 里 1,921 条条款,是**结构化表单**(固定三列 + 闭合的操作类型词表),不是自由文本。用确定性解析 + 两张人工维护的对照表把 `写/判断` 类条款直接生成清单条目,**不要用 LLM 逐条生成用例**。

## 实测:为什么这是解析问题,不是 AI 问题

`13通信` 的一条:

```
用例标题 | M_00_00_13_000101_01 通信_本地通信方式_红外通信_参数配置
要点     | 红外通信模式能配置为HDLC模式并能成功通信
步骤1 → 操作描述 | 表计只加电压上电
        操作类型 | 调整台体
        对象参数 | 接线方式="与表型一致" / Ua=Un / Ia=0 / θa=0° / Fre=Hz
步骤2 → 操作描述 | 设置红外通信模式为HDLC
        操作类型 | 写/判断
        对象参数 | 通信模式=HDLC / 波特率=9600bps
        预期结果 | 读写一致为合格
```

操作类型全表只有 67 种取值且高度集中(见 `36-manual-steps.md` 的表),归一化后是 8 个原子动作。`对象参数` 是 `键=值`。

## 三层结构

### 1. 解析器(`tools/import_cases.py`)

- 按表头定位:每个 sheet 的列数不同(5–40 列),**不能写死列号**,按 `用例标题 / 步骤N / 操作描述 / 操作类型 / 对象参数 / 预期结果` 这些**标签**定位
- 输出中间产物 `build/cases.json`(不要直接写 yaml:中间产物可以 diff、可以人工审)
- 保留原始行号,便于回溯

### 2. 归一化表(`configs/import/ops.yaml`)

67 种操作类型 → 8 个原子动作。变体是机械的:

```yaml
write: [写, 写/判断]
read:  [读, 读/判断]
bench: [调整台体]
wait:  [延时, 延迟]
manual: [人工操作, 人工操作/判断]
exec:  [执行, 执行/判断, 定时操作]
none:  ["/", ""]
```

### 3. 两张对照表(`configs/import/params.yaml` / `expects.yaml`)

```yaml
# 对象参数名 → 台架量 / 点表读数键
Ua: {device: bench, quantity: 电压, unit: V}
Active energy import (+A): {device: dut, key: 正向有功总电能}

# 预期结果短语 → 判据类型
读写一致为合格: {kind: equals}
读取成功为合格: {kind: exists}
设置成功为合格: {kind: equals, compare: written_value}
```

对照表**人工维护、进版本库**。模型可以辅助出候选(见下方),但**候选必须人工确认后固化成表** —— 猜错一个量名就是静默假读数。

## 覆盖率报表(必须先能回答"能自动多少")

导入器必须输出:

```
条款总数 1921
  可直接生成(全部步骤在映射表里)         N1 条
  部分可生成(含 manual 步骤,标待人工)     N2 条
  映射缺口(对象参数名不在对照表里)        N3 条  ← 列出前 50 个未映射名字,供人工补表
  结构异常(预期结果在合并单元格/图片)      N4 条
```

**先跑报表,再决定要不要继续**。如果 N3 很大,靠补对照表而不是靠模型。

## 不做

- 不用 LLM 逐条生成 yaml:不可复现、不可评审、每次结果不同,证据对不上
- 不把 `人工操作` 步骤丢掉(见 `36-manual-steps.md`)
- 不生成 `tests_scenario/` 用例:`写/判断` 类没有因果链,归 `setting_cases`
- 不解析 `07事件` 的 40 列表格里的附件/图片;那部分进"结构异常"栏
