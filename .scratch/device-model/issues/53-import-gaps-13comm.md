## 一、8 条结构异常(实测明细,不是"表格读不全"这种笼统说法)

```
7 条 no_expected:   判定步(写/判断)没有预期结果
  M_00_00_13_000101_09_1  步骤3@334
  M_00_00_13_000101_12_1  步骤3@671
  M_00_00_13_000102_09    步骤2@1139
  M_00_00_13_000102_0C    步骤3@1246、步骤22@1303
  M_00_00_13_000109_20    步骤1@3262
  M_00_00_13_000200_62    步骤3@3645
1 对重复编号:
  M_00_00_13_000A08_01 在本 sheet 出现两次(计 2 条异常)
```

### 决策(不许默认补,要出清单)

**不给"写/判断"默认补预期结果。** 看上去"读写一致为合格"是通用口径,但有的条款可能是"写失败也算合格"(见下面第二条 expect 短语)。默认补上去就是**替工程师下判定**,而且会静默生成一批可能错判的条款。

产出:**`docs/import-gaps-13通信.md`**,一张给写用例工程师的表,每行:

| 条款编号 | 表格行号 | 步骤 | 缺什么 | 需要我们拿到什么 |
|---|---|---|---|---|
| M_00_00_13_000101_09_1 | 334 | 步骤3 | 预期结果为空 | 这一步的合格判据(原文一句话即可) |
| M_00_00_13_000A08_01 | — | 重复编号 | 两条同名条款 | 合并成一条,还是其中一条改号(改成什么) |

**重复编号要单独强调**:它会让证据里两条记录同 id,归因分不开(这和 issue 24 定的"id 唯一"冲突)。

## 二、10 条映射缺口(实测明细)

```
符号值(不是数字):
  'Ua=Un' / 'Ub=Un' / 'Uc=Un'   ← Un 是额定电压
  'Fre=Hz'                       ← Hz 是额定频率
  '接线方式="与表型一致"'         ← 枚举取值
未知 expect 短语:
  '通信成功、表计正确回复为合格'
  '通信失败、表计无响应、无异常为合格'   ← 注意:失败也算合格,这条必须人定
```

### 三类分别处理

1. **符号值 `Un` / `In` / `Hz`** → 新增 `configs/import/symbols.yaml`,把符号映射到**型号参数名**(不是常数!):

   ```yaml
   Un: {param: rated_voltage_v, fallback: 220}   # 没有该参数时用 220?
   In: {param: rated_current_a}
   Hz: {param: rated_freq_hz, fallback: 50}
   ```

   `fallback` 必须先和工程师确认:**没有额定电压参数时用 220 还是拒收**。我倾向**拒收**(报"型号缺 rated_voltage_v"),因为 220/380 猜错的后果是台架设错电压,而那是"看起来正常"的错。

2. **`接线方式="与表型一致"`** → 属外部(台架枚举表,已在 `docs/external-inputs.md` 第 1 项)。**先留 TODO**,不猜。

3. **两条未知 expect 短语** → 进同一份 `docs/import-gaps-13通信.md` 的问询清单。第二条("通信失败…为合格")要特别标:**它和"失败=不合格"的直觉相反,必须由写用例的人确认这是本意**。
