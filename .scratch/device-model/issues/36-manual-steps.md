# 36 17% 的条款步骤是"人工操作",平台无处表达 → 导入时会静默少测

Status: resolved
Type: task
Blocked by: None — 必须在 xlsx 批量导入前做

**What to build:** 测试工程师那份 `表计功能测试用例V3.2.1.xlsx`(1,921 条条款)里,**7,589 步(约 17%)的操作类型是 `人工操作` / `人工操作/判断`** —— 切换上位机通信模式、目视看液晶显示、拔插卡。平台现在只能表达"自动跑的动作",这些步骤没有落点,导入器只能丢掉它们,而丢掉等于**静默减少 17% 覆盖**。

## 实测

全表 27 个 sheet、1,921 条条款的操作类型分布:

| 操作类型 | 步数 | 平台能做吗 |
|---|---|---|
| 写/判断 · 写 | 23,020 | 能(票 26 已交付) |
| 读/判断 · 读 | 17,639 | 能 |
| 调整台体 | 11,672 | 能 |
| 延时 · 延迟 | 9,825 | 能(`settle` / `hold`) |
| **人工操作 · 人工操作/判断** | **7,589** | **没有任何表达** |
| `/`(无操作) | 4,347 | 跳过 |
| 定时操作 · 执行/判断 等 | ~1,700 | 部分 |

## 期望

一个**显式的 `manual` 步骤类型**,三种落点都要有:

### 1. 清单层(setting_cases 里)

```yaml
M_00_00_13_000101_01:
  clause: "DL/T 645 …"
  steps:
    - {write: 通信模式, value: "HDLC", expect: "HDLC"}
    - {manual: "切换上位机通信模式为 HDLC", expect: "由操作员确认已切换"}
```

### 2. 结论语义

`manual` 步骤**不算通过、不算失败**,而是第三种状态:`pending_manual`。

- 该节点在报告里显示 `SKIPPED` 且原因写明"含 N 个待人工确认步骤"
- 归因里归到「没有有效结论」而不是「设备不合格」
- **绝不能默认当通过** —— 那是最危险的一种静默

### 3. 回填与证据

人工确认后要有地方写回:证据里留占位,操作员填 `confirmed: true/false` + 时间 + 人,再跑一次 `attribute_round.py` 时该条从 `pending_manual` 变成有效结论。

最小可做版:只需要在 `<设备>.jsonl` 里写 `{"kind": "manual_step", "action": ..., "expect": ..., "confirmed": null}`,回填工具可以后续再做。

## 不做

- 不做"人工步骤自动判过"(那是假通过)
- 不做 OCR/AI 去替代人工(上游有 OCR 能力,但那是另一个项目,先把落点留出来)
- 不把 `manual` 步骤编进 `verdict_of` 的失败集合(它不构成结论)

## 验收

- [x] `setting_cases` 支持 `manual` 步骤;`expect` 为文字说明
- [x] 含 `manual` 步骤的用例 → `pytest.skip`,原因里带"待人工确认 N 步",退出码仍是 0

- [x] 全量套件仍全绿
