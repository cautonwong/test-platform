# 设备模型改造:从 2 种设备到"非常多设备"

## Problem Statement

这个平台现在只认识两种设备(逆变器、电池),共 4 台实例。要接的是电表、新能源设备(逆变器 / EMS / IEMS / HEMS / 电池)、电力采集终端、配网终端 —— 类型 6~10 种、实例几百台、型号几十个。

按现在的骨架直接扩,会撞上四堵墙:

1. **判据写死在代码里。** 45–55Hz 和额定功率上限是类常量,60Hz 出口机型改不了;更糟的是读数超范围会抛异常,坏设备只能得到 error,拿不到"实测 60Hz"这份证据 —— 平台的职责是判设备不合格,不是自己崩掉。
2. **没有"周边设备"。** 测防孤岛要控制电网模拟器,测过载要可调负载。现在只能把硬件依赖藏进驱动内部,三台被测设备共用一台模拟器时无法共享,周边设备坏了还会被误判成被测设备不合格。
3. **200 台设备手写清单不可维护。** 型号只有 6 种,点表却在 200 条记录里重复 200 次;同一条 RS485 总线上的表还会被并行跑到串话。
4. **用例没有身份、证据为零。** 报告引用不了"依据 DL/T 645 条款 4.5.2";失败时说不出设备到底回了什么;没法只跑某型号、只重跑失败。

## Solution

把设备清单从"扁平的设备数组"升级成**三段式声明**:判据集、型号、设备实例。型号承担点表 / 能力 / 判据集的一次性声明,设备实例只引用型号名和接入位置。

把"合格与否"从聚合根里搬出来:聚合根只保护**不变量**(未连接就读数、SOC 超出 0–100),读数永远被记录;是否合格由**判据集**求值得出,证据随每台设备落盘。

把终端和周边设备收进同一个设备模型,用两个字段区分身份:`role`(被测 / 周边)和 `via:`(挂在哪台终端下面)。总线拓扑天然约束并行度 —— 同一终端下的设备串行,不同终端之间并行。

用例仍是 pytest 函数,但每条带结构化元数据(编号、标准条款、标签),既能被 `--select` 筛选,也能自动写进证据包。新增用例的门槛靠模板和 agent 代写来降,不靠自制 DSL。

## User Stories

**设备与型号**

1. 作为测试工程师,我想在清单里按型号声明点表和能力,只写一次,这样新增 200 台同型号设备时不用重复 200 遍。
2. 作为测试工程师,我只在设备实例上写 `id`、型号名、接入位置和总线地址,这样新增一台设备的配置能在一分钟内写完。
3. 作为平台开发者,我想让设备类型按"大类 × 规约"划分(电表 / 逆变器 / 电池 × DL/T645 / Modbus / 串口…),这样厂家和型号差异不会让注册表线性膨胀。
4. 作为平台开发者,我想在清单校验阶段就发现"引用了不存在的型号"或"型号声明了不支持的规约",这样错误在装配前暴露而不是跑到一半。
5. 作为测试工程师,我想给设备声明能力(有功电量、无功电量、电压…),这样不支持某能力的设备会被跳过而不是报假失败。
6. 作为测试工程师,我想在个别设备上覆盖型号级的判据,这样 10 台 60Hz 机型能和 190 台 50Hz 机型共存于一份清单。

**判据与不变量**

7. 作为测试工程师,我想让读数永远被记录,即使超出判据范围,这样坏设备也能留下"实测 60Hz"这份证据。
8. 作为平台开发者,我想让聚合根只在违反不变量时抛错(未连接、SOC 越界),这样"平台有 bug"和"设备不合格"不会再混为一谈。
9. 作为测试工程师,我想让判据集按整机具名声明并被设备引用,这样改一次判据不用改 200 处。
10. 作为验收人员,我想在报告里看到"这台设备适用哪套判据、实测多少、结论是什么",这样结论可复核。
11. 作为测试工程师,我想在判据求值失败时看到超出多少而不是只有一句 assert,这样判断是设备边缘偏差还是彻底故障。

**周边设备**

12. 作为测试工程师,我想把电网模拟器、可调负载、标准源当作设备写进清单并标 `role: support`,这样我不用把硬件控制藏进被测设备的驱动里。
13. 作为测试工程师,我想让多台被测设备共用一台周边设备,这样不必为每台被测设备配一套台架。
14. 作为平台开发者,我想让周边设备先于被测设备连接,这样被测设备的用例开始时台架已经就位。
15. 作为测试工程师,我想在周边设备故障时看到"测试无效"而不是"被测设备不合格",这样不会冤枉设备。
16. 作为测试工程师,我想让周边设备不参与一致性判定,这样它们不会被当成被测设备判合格/不合格。

**拓扑与终端**

17. 作为测试工程师,我想让采集终端 / 配网终端既作为被测设备、也作为下游设备的接入通路,这样台区里"终端 + 20 块表"能被完整测试。
18. 作为测试工程师,我想在设备上用 `via:` 声明它挂在哪台终端下,这样装配顺序和总线归属都由清单决定,不用代码分叉。
19. 作为测试工程师,我想让挂在同一终端下的设备串行执行、不同终端之间并行,这样不会因为抢总线出现随机失败。
20. 作为平台开发者,我想让下游设备的连接只负责选中从站地址,物理连接归终端,这样总线的生命周期只有一个所有者。
21. 作为测试工程师,我想在清单里写错 `via:` 指向不存在的终端时立刻收到明确报错,这样不会静默测到零台设备。

**证据**

22. 作为验收人员,我想每台设备留一份证据(原始报文 hex、解码读数、适用判据、结论),这样任何一个结论都能复现。
23. 作为测试工程师,我想让失败的用例一定有证据落盘,这样不用为了复现去重跑。
24. 作为平台开发者,我想用装饰器包一层传输把收发记下来,这样驱动层和领域层一行都不用改。
25. 作为验收人员,我想让证据目录按会话隔离(`evidence/<时间戳>/`),这样多次运行不会互相覆盖。
26. 作为 CI,我想让证据文件机器可读,这样能被流水线收集归档。

**用例管理与过滤**

27. 作为测试工程师,我想给每条用例声明编号、标准条款和标签,这样报告能引用"依据 DL/T 645 4.5.2"。
28. 作为测试工程师,我想只跑某个型号的用例,这样出厂抽检不用等全量跑完。
29. 作为测试工程师,我想只跑支持某能力的设备,这样不会把不支持无功的表判成失败。
30. 作为测试工程师,我想只跑某类测试项(通信 / 精度 / 保护),这样能按需出分区报告。
31. 作为测试工程师,我想只重跑上次失败的用例,这样修完一台设备能快速确认。
32. 作为平台开发者,我想让用例元数据只有一份事实源(测试函数本身),这样不会出现清单和代码漂移。
33. 作为不会写 Python 的测试工程师,我想用一句话描述需求让 agent 生成用例并让我审核,这样我也能扩展测试项而不用学编程。

**两层测试与清单来源**

34. 作为平台开发者,我想让一致性测试层只对 `role: dut` 的设备按类型展开,这样周边设备不会混进契约测试。
35. 作为测试工程师,我想让场景测试层独立成目录并显式列出参与的设备和周边设备,这样跨设备用例不会污染逐台判定。
36. 作为测试工程师,我想从资产台账(Excel/CSV)生成设备清单,这样不用手工录入几百条。
37. 作为测试工程师,我想让生成的清单进版本库、可 diff,这样设备变更历史看得见。

**接入新设备(高频动作,门槛是核心指标)**

38. 作为测试工程师,我想在接入一个同规约的新型号时只改配置、不新增任何 Python 文件,这样 200 台设备里陆续换型号不用排队找开发。
39. 作为平台开发者,我想让协议知识(拼帧、校验、字节序、编码)独立成一层,而不是每加一类设备就重写一遍 DL/T645 和 Modbus 的帧格式。
40. 作为测试工程师,我想按“无功电量”这样的读数键取物理量,而不是记每种设备各不相同的驱动方法名。
41. 作为测试工程师,我想让设备缺少某能力时相关用例自动跳过,这样我不会靠手写条件判断去防假失败。
42. 作为平台开发者,我想让第二个规约接入时不需要改动通用读取路径,这样“复用”不是口头承诺而是验收标准。

## Implementation Decisions

**配置结构(三段式,这是 schema 决策)**

清单从"设备数组"变成四段:`criteria_profiles`(具名判据集)、`models`(型号级模板)、`devices`(实例)、`test_matrix`(型号 → 适用测试项)。设备实例只允许引用型号,不允许内联点表。

```yaml
criteria_profiles:
  grid_50hz_0.5s: { freq: [45, 55], accuracy_class: "0.5S" }
models:
  dtsd1352:
    type: meter
    protocol: dlt645
    criteria: grid_50hz_0.5s
    capabilities: [有功电量, 电压]
    point_table: { voltage: "02010100", energy: "00010000" }
devices:
  - { id: m_001, model: dtsd1352, role: dut, via: terminal_01, bus_address: 1 }
  - { id: sim_grid_01, model: chroma_61800, role: support }
test_matrix:
  - { model: dtsd1352, items: [电压精度, 有功电量精度] }
```

**分层:协议知识独立成层**

依赖方向自上而下,每层只认识下一层:

```
transport    字节管道(已有)
   ↓
protocol     通用协议编解码:帧格式、校验、字节序、编码(新增)
   ↓
点表          型号级声明:地址、长度、编码、倍率、字节序、单位(配置,非代码)
   ↓
drivers      点表驱动的通用读取路径 + 复杂设备的专用出口
   ↓
domain       聚合根,不认识任何协议细节(已有)
```

- 读数键就是点表项的键:用例按“无功电量”取数,不依赖任何具体驱动类的方法名。
- 通用读取路径只允许“一组点 → 一次领域方法调用”。配置里不允许条件、循环、时序;需要分支的设备写专用驱动,并可复用协议层与点表求值。
- 接入新设备的三级门槛是验收指标:同规约新型号 = 零 Python 文件;新规约 = 一个编解码模块;新大类 = 一个聚合根 + 配置。

**领域事件:软信号不走异常**

已合入上游的事件层:聚合根把“值得外界知道、但不中断本次调用”的事实记入内部队列(`_raise_event`),外部在合适时机 `pull_events()` 取走,交给 `EventSink`。目前有内存与日志两个实现,由 pytest 插件在每条用例后收集、会话结束时汇总打印。

- 这是“不变量 vs 验收判据”之外的第三条通道:硬违反 → 抛错;判定不合格 → 记录 + 判据结论;软信号 → 领域事件。
- 现有软告警阈值(功率 > 额定 90%、SOC < 10%)写死在聚合根里,必须随判据集一起下沉,否则 60Hz 与外购机型改不了。
- 事件目前只进内存并打印,不进证据。证据层要增加一个 JSONL 的 `EventSink` 实现,让报文与事件落进同一份证据。
- 事件收集目前是 autouse 且依赖装配结果,导致平台自身单测也需要合法设备清单。设备层的收尾不应抬高单测门槛。

**领域层**

- 新增"判据"值对象:纯数据 + 求值,不依赖协议、不依赖设备类型。
- 聚合根的 `record_reading` 不再校验判据范围,一律记录,并在读数上标记是否超限。判据求值移动到用例/判据对象。
- 聚合根保留的不变量只有:未连接不得读写、SOC 落在 0–100、额定容量为正。
- 现有"拒绝非法读数"的一组单测语义反转:从"抛错"变成"记录 + 标记超限"。

**注册与装配**

- 设备工厂的注册键从单一设备类型改为 `(设备类型, 规约)` 二元组,与传输层的 `(协议, 模式)` 键对称。
- 组合根按依赖顺序装配:先周边设备,再终端,最后挂在下游的设备;`via:` 构成拓扑边,装配前做存在性与环路校验。
- 领域对象接收判据集(型号级 + 设备级覆盖合并后的结果),不再持有硬编码阈值。
- 新增电表与终端两类驱动:电表走规约字节流,终端同时满足"设备"和"字节流传输"两种形状(结构化类型,不引入继承)。
- 下游设备的连接语义:只选中从站地址,不建立物理连接;物理连接由终端负责。

**证据**

- 用装饰器包一层传输实现记录:对外仍是同一个传输协议形状,内部把每次收发的原始字节、时间戳、解码结果落到 JSONL。
- 证据目录按会话时间戳隔离,每台被测设备一份文件;用例元数据随每条记录写入。
- 装饰器先覆盖最常用的字节流协议族,其余协议族等真实需求出现再补。

**用例组织**

- 新增 `@case` 装饰器携带编号、标准条款、标签;元数据的唯一事实源是测试函数本身,不建第二份清单。
- 新增统一过滤入口,支持按型号、能力、标签筛选;失败重跑复用 pytest 自带机制。
- 契约测试的展开条件从"按设备类型"变为"按设备类型 **且** `role: dut`"。
- 并行执行按拓扑分组:同一 `via:` 下的设备进同一组,组内串行、组间并行。
- 场景测试层只留空目录和一条约定(必须显式列出参与的被测设备与周边设备),不建任何抽象。

**文档**

- `CONTEXT.md` 已同步 15 个术语:被测设备 / 周边设备 / 设备实例 / 设备类型 / 型号 / 能力 / 点表 / 判据集 / 验收判据 / 不变量 / 证据 / 总线 / 拓扑 / 一致性测试 / 场景测试 / 测试层 / 测试项。
- 术语表只放词汇,不放实现细节。

## Testing Decisions

**什么样的测试算好测试**

只测外部行为:给定一份设备清单,装配出的平台对外表现是什么;给定一串读数,判据给出的结论是什么。不测内部方法调用次数、不测私有字段、不测装饰器注册表的具体形状 —— 那些是重构就会变的东西。

**缝(shard)只有两个,全部是现有缝**

1. **`CompositionRoot.build(清单路径)`** —— 主缝,覆盖 13 项决策里的 9 项。用例构造临时清单 → 装配 → 断言对外可见的结果:型号展开后的设备集合、`role` 先后顺序、`via:` 拓扑、判据合并结果、注册键解析、test_matrix 展开、证据文件落盘。不需要真实设备,也不需要模拟器。
2. **聚合根直接构造** —— 覆盖不变量与判据求值。纯 Python,毫秒级。现有 prior art:`tests/test_inverter.py` 的"类级别不变量"组、`tests_unit/` 里的鸭子类型 fake。

3. **协议编解码(纯函数)** —— 新层带来的新缝:给点表项 + 原始字节,断言解出的物理量;给物理量,断言拼出的帧。不需要设备、不需要传输。允许出现第三个缝的唯一理由:它是纯函数,测试成本接近零,而换算与字节序的错误在报告里表现为“读数差 100 倍”,最难查。

**刻意不为证据建缝:** 证据不单独为记录装饰器写用例,而是从缝 1 装配后读 JSONL 断言。少一个缝,少一处重构就失效的测试。

**会被改写的既有测试**

- `tests/test_inverter.py` 中"拒绝非法读数"的参数化组(4 条)→ 改为"记录 + 标记超限"。
- 契约测试的展开依赖从"类型"改为"类型 + role",现有逆变器用例行为不变(默认 role 为 dut)。
- `tests/conftest.py` 的硬编码类型分支要改成注册表驱动,否则每新增一种设备类型都要手改三处。

**验证限制**

当前环境没有 pytest,也无网络安装依赖。改造期只能做语法与导入级自检,真正的套件验证需要在有依赖的环境执行。

## Out of Scope

- 场景测试层的用例与抽象(只留空目录和约定,形状等第一个真实场景需求)
- 台账导入脚本的具体实现(决策已定:CSV/Excel → 清单,清单进版本库;实现另开)
- 电表与终端的真实报文格式(需要现场样本,现有驱动按已确立的字节协议风格写)
- 步骤级 DSL / 配置化测试项(明确否决)
- 平台的 Web 界面、数据库、用例管理服务(明确否决)
- 全量收发录制与离线重放
- 设备的完整状态机(初始化 / 锁定 / 升级中等状态)
- 模拟器保真度(故障注入、抖动、超时模拟)

## Further Notes

- **决策的代价已经认下,不要在实现时两头都要:** 型号差异只能靠配置表达,代码里不能按厂家分叉;新增断言逻辑必须会 Python;400 台以上设备才需要重新考虑清单的人机界面。
- **三个建议固化为 ADR 的决策:**(1) 设备类型 = 大类 × 规约,型号差异只在配置;(2) 测试项用 pytest 代码写,门槛靠模板与 agent 代写而非 DSL;(3) 终端与周边设备进入同一设备模型,靠 `role` 与 `via:` 区分身份。
- **一个已知陷阱:** 只重跑失败的机制按测试节点缓存,设备清单变更后缓存会失配,文档里要写明。
- 改造顺序有依赖:领域层 → 配置层 → 装配层 → 证据与用例元数据 → 并行分组与收尾。前一步不完成,后一步的用例会建在会变的接口上。
- **合入上游时发现的两个既存问题(已记为 1b):** 一是会话级装配下聚合根共用,断言历史绝对值的用例随执行顺序变化(单条跑绿、全量跑红);二是 autouse 的事件收集 fixture 让平台自身单测也要求合法设备清单 —— 上游声称跑绿,但那份绿从未被真正执行过。
- 本机虚拟环境有 pytest 但没有并行插件,并行分组那张票的验收无法在这里完成。
